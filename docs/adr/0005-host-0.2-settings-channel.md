# ADR-0005:设置通道整体迁移到宿主 Config schema — 0.2.x 适配

- 状态:已接受
- 日期:2026-10-20

## 背景

宿主 0.2.1-rc.2 把插件设置的三条旧通道全部移除(对宿主 `node_modules/@deepseek-ai/` 全量 grep 实证,零命中):

| 旧通道 | 0.1.x 用法 | 0.2.1-rc.2 实况 |
| --- | --- | --- |
| `installSettingsSection`(包导出) | 宿主端注册设置区 | 不存在 |
| `settingsNamespace`(包导出) | 设置命名空间常量 | 不存在 |
| `ctx.settings.installSection(...)` | 服务方法 | 不存在 |
| `settingsScope`(客户端服务) | `ctx.settingsScope.bind({namespace})` | 不存在(宿主与全部 60+ `dsh-client-*` 包零命中) |
| `settings.plugin.item`(客户端槽位) | 设置卡注册点 | 不存在 |

启动日志的两条降级与此一致:`settings-api-missing`,以及 `descriptor-version-resolved {"version":3,"channel":"pin-latest"}` + `deps-resolution-failed`(宿主包目录一个都没定位到)。

同时新增了两处承重机制:

- **服务端**:`dsh-settings` 的 `SettingsForms` 从 `entry.fiber.runtime.Config` 反投影生成表单——`volatileForm(schema)` 只投影标了 `.volatile()` 的字段,命名空间是 profile patch 的 entry id(本插件 `prompt-enhancer`);cordis 4.0.5 的 `resolveConfig` 用该 schema 校验后作为 `apply(ctx, config)` 第二参传入,volatile 字段在运行时是引用对象 `{get()}`。
- **客户端**:`configForms` 服务(`ConfigForms.get(id)` → `ConfigFormController`,写操作返回 `Promise<boolean>`) + `settings.plugins.tab` 槽位(注册项用 `id` + `label`);`settings.plugin.item` 被官方占满且文档明示插件配置不应放那里。全宿主没有任何包注册 `plugins.bundle.config` / `plugins.row.config`,即宿主**不会**替插件自动画表单。

另有一处模块解析硬约束:vendor(linked)插件的裸 `@deepseek-ai/*` import 要被路由进宿主依赖树,必须满足「resolution 表有条目 **且** 插件 `package.json` 的 `peerDependencies` 声明了该包名」(`dsh-app-boot` 的 `routeLinked`);兼容性判定只校验 `@deepseek-ai/dsh*` 命名的 peerDeps。

## 决策

1. **设置能力只走 0.2.x 官方 seam**:新增 `src/config.js`,导出 volatile 的 `Config` schema(`model` / `intensity` / `outputEnglish`),`apply(ctx, config)` 用 `bindConfigSource` 把校验后的配置按 ctx 存进 `WeakMap`(每 ctx 一个配置源,避免多 profile 串味),`enhanceConfig(ctx)` 逐键 `.get()` 并 `structuredClone`。旧三通道代码全部删除,不做运行时探测。
2. **schemastery 用失败可降级的动态 import**:`try { await import("@deepseek-ai/schemastery") } catch {}`,解析不到时 `Config` 为 `undefined`;cordis 的 `resolveConfig` 见 `!runtime.Config` 会跳过校验,插件仍能加载(此时 `apply` 收到 profile patch 原文,功能降级但不断链)——静态 import 会把解析失败升级成整模块加载失败。
3. **客户端设置卡改 `configForms` + `settings.plugins.tab`**:`settingsCardControllerFor(scope)` 接收 `ConfigFormController`;`save()` 里每次写操作判 `=== false`(宿主拒绝时 recover 后返回 `false` 而非抛异常),并回读 `getSnapshot().user` 校验落地;静态 `inject` 把 `settingsScope` 换成 `configForms`,槽位注册项从 `key` 改为 `id` + `label`。
4. **支持面收敛为 0.2.0+**,版本要求写进 `peerDependencies`(`@deepseek-ai/dsh*` 锚 `^0.2.0-rc.2`,`schemastery` 锚 `^3.18.4`,`dsh.client.inject` 补 `dsh-client-ui-settings`),由宿主在加载前按版本不满足拒绝;不在插件内做跨代兼容分支。
5. **宿主包定位不再写死发行版目录名**:`findPackageDir` 在原有候选根之外补「包自身 `../node_modules`(管理包自带依赖图)」「宿主 bin(`process.argv[1]`)逐级上溯」「win32 扫 `%APPDATA%` 下所有含 `dependencies/dsh/node_modules` 的目录」——本机此前定位失败正是因为候选里只写了 `io.github.hairyf.deepseek-harness-desktop`,而桌面端实际目录是 `dsh-tauri`。

## 后果

- 正面:0.2.x 上设置卡与配置即时生效恢复;`descriptor-version-resolved` 从 `pin-latest` 回到 `import`(实测能定位到宿主 `dsh-subagent`,`lib/types/descriptor.js` 常量 = 3);模块路由靠 peerDeps 声明即可,不再依赖宿主侧补丁。
- 代价:0.1.x 用户从此不可用(由 peerDeps 在加载前显式拒绝,不是静默失效),他们需留用插件 0.1.3;README「宿主兼容」与 `docs/VERIFICATION.md` 第 20 项同步记录。
- 约束:`Config` schema 的字段改动是**面向宿主的公开契约**——删字段等于删用户已存配置,加字段必须给默认值;`.volatile()` 不能重复包装、不能嵌在 volatile 对象里(schemastery 直接抛错)。
- 约束:测试锚点仍靠源码字符串切片,`src/config.js` 是新增文件,`scripts/build.mjs` 必须把它一起校验拷贝(已在构建脚本的产物清单里)。

## 替代方案(否决)

- **双通道共存(旧 `settingsScope` + 新 `configForms` 各注册一次)**:`inject` 是静态数组,旧服务缺失会让整个客户端插件不加载(不是局部降级);`ctx.inject([...])` 作用域注入虽可绕过,但宿主全部 60+ 客户端包无一使用该形态,等于自创一条未经宿主验证的路径——用一个未验证的机制去保一个已被宿主删除的通道,风险高于收益。
- **运行时探测服务是否存在再决定接线**:cordis 严格模式下未 inject 的属性访问直接抛错,探测本身就要靠异常兜,等价于把「插件能不能用」交给 catch。
- **只用 `Config` 不注册客户端卡片(让宿主自动画表单)**:`dsh-settings` 的 `describe()` 只输出数据,`autoGenerate` 在全宿主客户端零命中,没有任何包消费它渲染 UI——不注册就永远没有设置界面。
- **把裸 import 换成 `createRequire` / 绝对路径拼装**:宿主对 linked 插件的路由是以「裸 specifier + peerDeps 声明」为条件的,绕开它等于放弃宿主依赖树的版本一致性(还可能拿到另一份 schemastery 实例)。
