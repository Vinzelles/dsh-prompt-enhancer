# ADR-0001:强化执行通道 — 隔离子会话 agent 为主,llm 直调为降级

- 状态:已接受
- 日期:2026-08-19

## 背景

「强化」需要一次模型调用:输入 = 原始提示词 + 有界对话上下文 + 工作目录内检索到的相关文件;输出 = 增强提示词。候选通道有三:

1. **通道 A:llm 直调** — 插件在 host 内解析会话的 provider/model 路由,`ctx.llm.stream` 单次调用,检索由插件自己完成(glob/grep/read 的有界扫描)。
2. **通道 B:隔离子会话 agent** — `ctx.agents.create` 建临时子会话(继承父会话工具组合 + 只读工具限制 + 强化专用 persona),`agent.followup` 跑一轮完整 agent 循环(带工具,文件定位由 agent 自己完成),读回子会话末条助手消息后 `dispose`,主会话历史零污染。
3. **通道 C:主会话内半可见调用** — 在用户当前会话里注入一条消息并读取回复(会污染主历史,且与「还原/手动发送」的交互语义冲突)。

## 决策

采用 **B 为主、A 为降级**。B 超时 90s;A 在 B 的创建或执行失败时兜底,超时 60s。两者共用同一 persona 与 payload 结构。

## 理由

1. **语义一致**:用户需求明言「整个功能与给子代理写任务提示词类似」。通道 B 让「定位关联文件」由 agent 的工具调用完成,而不是插件自建检索器——检索质量、检索边界的控制都随模型能力走,且天然遵守仓库已有的 ignore/观察策略。
2. **零污染**:子会话独立 `sessionId`,历史不进主对话;「还原」只需回退草稿文本,无需清理会话记录。
3. **降级保底**:通道 B 依赖 agent 工厂、工具组合、父会话存活等较多前置条件;A 只需 llm 服务与路由,保证「强化」在任何可发消息的会话里都可用(降级时无文件检索,输出纯改写,与「零命中静默降级」的产品语义一致)。

## 后果

- 正面:检索交给 agent;主历史干净;两条通道的 persona 与输出格式共享同一份定义,行为一致。
- 负面:通道 B 需要创建/销毁临时子会话,延迟与 token 成本高于纯直调;无工具时(composeFrom 失败)B 退化为纯改写,由 A 兜底同语义。
- 风险与缓解:子会话可能继承父预设的宽工具面 → 用 `tools.restrict({allow: [glob, grep, read]})` 收紧为只读;限制注册失败(工具名未知)时不阻断创建、仅告警退化。超时通过 `activityDone` + 定时器竞争实现,超时即 `agent.cancel` 并 dispose。
