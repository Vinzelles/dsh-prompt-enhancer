# 验收清单（10 项功能基线，发布/回归自查）

1. 输入框右侧出现「强化」图标；草稿为空时禁用。
2. 点击强化 → 图标转 spinner → 输入卡片出现加载遮罩（含「取消」按钮，输入被锁定）→ 草稿被增强文本替换（手动发送）。
3. 强化成功后出现「还原」；点击还原草稿回退原文且还原消失。
4. 手动编辑草稿 / 发送消息后还原消失（严格触发）。
5. 强化期间点「取消」：遮罩消失、草稿保持原文、host 端直调请求被中止。
6. 参考文件清单均为真实存在的文件（路径臆造会被自动剔除）；无仓库/零命中时无该节（静默降级）。
7. 失败/超时 toast 提示，原文保留，可重试。
8. 设置 → 内置插件 → Tab「提示词强化」出现设置表单：模型下拉含「跟随会话默认」+ 宿主选择器同源的 provider/模型/思考强度（含 workbuddy、openai-codex 等插件模型）；diag 不得出现 `settings-card-failed` / `remote.session`；强度三档可切换；保存写入 plugin config（`home/profiles/<profile>/cordis.patch.yml` 中 `id: prompt-enhancer` 的 `config` 段），`configForms` 写操作返回 `true`（宿主拒绝时为 `false`，卡片置保存失败态而不抛异常）。
9. 强度设为「低」后强化：输出精简且不含「## 参考文件」节；「中」仅列参考路径；「高」恢复完整引用（路径 + 说明）。
10. 配置专用模型后强化：diag log `enhance-start` 的 `model` 字段与宿主 `debug-stream.log` 的 `buildRequest done: provider=..., model=...` 显示该模型。
11. 运行在非标准 agent 预设上的会话点击强化不报错（2026-11-13 修订）：线上强化不再创建子会话，因此父预设首轮机制不再作用于强化路径；点强化只走 `ctx.llm.stream`，toast 不再因 `enhance-child-no-text` 出现「LLM 无输出」。旧的裸子会话重试记录仅保留在未调用的通道 B 实现与单测中。
13. 访问控制（2026-08-27）：非本机来源（非 `127.0.0.1`/`::1`/`::ffff:127.0.0.1`）调用 `/prompt-enhancer`、`/prompt-enhancer/models`、`/prompt-enhancer/diag` 任一端点，立即 403 且不执行业务逻辑（diag log 落 `foreign-request-rejected` 信标含来源地址）；本机来源一切行为正常（1–12 项全部成立）。缺失 socket 信息按非本机处理（fail-closed）。
14. 截断检测（2026-08-27，2026-11-13 修订为线上仅通道 A）：直调输出被 maxTokens 截断时捕获 finish 块 `reason.kind === "max-tokens"`——响应 JSON 携带 `truncated: true`，UI 弹显式告警 toast（增强稿仍替换、「还原 ↺」可用），host 落 `enhance-truncated` 信标（`channel: "llm"` 与草稿长度）、client 落同名信标。未截断时响应无 `truncated` 字段、UI 无告警（1–13 项行为不变）。通道 B 的 `childOutputTruncated` 仍保留在源码与单测中，线上强化不再走。
15. 草稿上限与意图分类（2026-08-27）：草稿超过 200000 字符时端点立即 400（错误信息含上限值，diag log 落 `enhance-draft-too-long`），不发起任何 LLM 调用；恰好 200000 字符正常处理。persona 规则 10（意图先行）：增强稿按意图类别组织（排查/实现/解释/简单问答四分类），缺关键背景时不发明事实而是写「结合项目代码/日志确认……」，一句话多问题拆编号子问题，原话已完整清晰时只做最小必要改写。
16. 转换英文开关（2026-09-05）：设置 → 内置插件 → Tab「提示词强化」出现「转换英文」开关（默认关）。开启后强化：输出全部为英文（参考文件节标题为 `## Reference Files`；skill 引用丢失时宿主确定性回填的节标题为 `## Skill References`）；路径存在性校验、中档压缩（只留路径）、低档剥离（整节删除）对英文标题同样生效（臆造路径照常剔除）；skill 引用记号、文件路径原样保留不翻译；关闭时行为与 1–15 项完全一致（输出跟随输入语言）。diag log `enhance-start` 携带 `outputEnglish` 字段。
17. 双代宿主身份契约—版本（2026-09-07 回归）：宿主 0.1.1（descriptor v2）与 0.1.2+（v3）下点击强化，diag log `descriptor-version-resolved` 的 `version` 与该宿主 dsh-subagent 的 `SUBAGENT_DESCRIPTOR_VERSION` 一致、`channel` 记录解析通道（import / scan / package-version / 缺省 pin）。在 0.1.1 宿主机上把插件临时改回硬编码 `version: 2` 会复现损坏（旧行为），改回 `descriptorVersion` 即恢复——本项保证「兼容当前宿主且不砸老宿主」。**注（2026-09-12 修正）**：本项此前声称「子会话均正常显示 one-shot 子代理身份、不出现会话记录损坏」，实际并未验证——它只锚了载荷形状，没锚载荷是否落盘。当时的落点（`childCtx.agent.session.append`）在任何一代宿主上都不成立，线上之所以还在写 descriptor（08-21~09-10 共 69 个子会话）是因为部署目录跑的是另一份手工同步的产物；09-11 迁移把产物刷回提交形态后归零。损坏的完整判定与取证见第 19 项与 ADR-0004。
18. 双代宿主 store 引擎契约（2026-09-10 回归）：宿主 0.1.1 与 0.1.2+ 下客户端均正常加载，输入框出现「强化」图标，diag log 依次落 `apply` → `slot-declared-callback` → `mounted`（有活动会话时），且不出现「平台快照 store 引擎缺失，已退回本地实现」告警。引擎在运行时逐条查表：`@deepseek-ai/dsh-client-store`（0.1.2+ 启动壳预置的平台种子）优先，`@deepseek-ai/dsh-client-runtime/client`（0.1.1 真实预载模块）兜底，两条都查不到才退回本地等价实现（observable 契约 `getSnapshot`/`subscribe`/`update`/`set` 不变）。反向验证：把工厂顶部改回 `const { createSnapshotStore } = require("@deepseek-ai/dsh-client-runtime/client")` 静态解构，在未打补丁的 0.1.2-rc.1 内核上启动页即报 `Failed to load plugins` + `client-modules: require(...) missed the module table`（静态 require 落空会中止整条 loader entry，插件全部功能不加载，不是局部降级），`tests/client-store-resolution.test.mjs` 同步转红。本项保证「插件自带跨版解析，不依赖任何宿主侧补丁」。
19. 子代理身份事件「落点」契约（2026-09-12 事故回归）：点击强化后，子会话日志（`~/.dsh/sessions/<cwd>/<childId>/session.v*.jsonl.zstd`）中**必须**存在且仅存在一条 `subagent/descriptor`（`version` = 宿主常量、`mode: "one-shot"`、`provider: "prompt-enhancer"`、`label: "提示词强化"`），且落在会话自身的事件后缀里——首选落点在 setup 窗口（`session/end-seed` 之后、`turn/start` 之前），兜底落点在首个 step 的回合内（`descriptorPath: "pre-step"`）；子代理目录该行显示为 `提示词强化 · 单次 · 已结束`（`activity: inactive`），**不出现**「会话记录损坏」。取证链：① diag log `enhance-child-ready` 的 `descriptorAppended` / `descriptorArmed` / `descriptorPath`（`setup-arg` = setup 第二参 / `pre-step` = 首步兜底），以及 `enhance-child-descriptor-final` 的 `descriptorAppended` / `descriptorPath` / `descriptorEvents`（条数取自会话日志本身，读日志时以此为准：`-final` 是终局审计，`-ready` 只是创建窗口快照）；② 不存在 `enhance-child-descriptor-unarmed` 信标；③ 把该日志事件喂给宿主真实 `subagentIdentityProjectionDefinition` 折叠出的值非 `null`（`null` 即 corrupt）。旧宿主（0.1.1/0.1.2）`setup` 只收一个参数，落点必然是 `pre-step`——两代都要能落盘才算通过。反向验证：把追加改回事故形态 `childCtx.agent.session.append(...)`（ctx 上无 `agent` 服务，服务名是 `agents`）→ 日志里 descriptor 条数归零、`enhance-child-descriptor-final` 落 `descriptorEvents: 0`、子代理目录立刻显示「会话记录损坏」，`tests/descriptor-append.test.mjs` 同步转红。
20. 宿主 0.2.x 设置通道与依赖解析（2026-10-20 升级回归）：在宿主 0.2.1-rc.2 上——① diag log 出现 `config-bound`（`keys` 含 `model`/`intensity`/`outputEnglish`），说明 cordis 用插件导出的 `Config` 完成校验并把 volatile 配置下发给 `apply(ctx, config)`；② `descriptor-version-resolved` 的 `version` 为 `3`、`channel` 为 `import`（宿主包定位成功，不再降级为 `pin-latest`），且**不出现** `deps-resolution-failed`；③ 客户端 diag 依次落 `factory-executed` → `apply` → `mounted`，不出现「cannot get property configForms without inject」类 cordis 严格模式报错，设置页「内置插件」下出现「提示词强化」Tab；④ 改设置并保存后，`cordis.patch.yml` 的 `config` 段更新且无需重启即刻生效（再点强化，diag log `enhance-start` 的 `intensity`/`outputEnglish`/`model` 反映新值）。反向验证：把 `package.json` 的 `peerDependencies` 中 `@deepseek-ai/schemastery` 删掉 → 裸 import 无法被路由，`Config` 退化为 `undefined`（`config-bound` 仍落但取值来自 profile patch 原文，设置卡片表单不再渲染）；把 `src/config.js` 的三个字段去掉 `.volatile()` → `dsh-settings` 的 `volatileForm` 返回 `undefined`，`configForms.describe()` 不含该 namespace，卡片注册后取不到 form。
